# One door per thing

A design for splitting `emerge-mapper` into five doors — Kits, Tiles, Compose, Maps, Rigs — so that
entering one shows only what that thing needs. Written after measuring the current behaviour rather
than from memory; every number below was read out of the code on 2026-08-16.

**Status: built — two doors, not five.**

The five-door version landed first and its own build produced the measurement that ruled it out:
**four shipped guides crossed doors mid-flow**, `room_from_nothing.json` seven times, and
`ComposeState::armed` — the state the Compose→Map half of that needs — does not survive a process
boundary. Chosen at the keyboard on the evidence, 2026-08-16: *"Kit and Map, two doors."*

So the boundary went where the **entity** changes rather than where the panel does:

| Door | Panels | The thing |
|---|---|---|
| **Kit** | Meshes → Tiles → Compose | make reusable content |
| **Map** | Map | build the level out of it |
| **Rigs** | Anim | the rig bench — crosses with neither |

Meshes, Tiles and Compose are not three jobs; they are one job at three levels of assembly, and an
author walks up and down that ladder constantly while making one kit. Splitting them put a process
boundary inside a single act. Keeping them together dissolved it: **all four cross-door guides walk
end to end again**, including `room_from_nothing`.

The strip survives, scoped: it lists what *this door* holds, so the Kit door offers three panels and
never the Map. `Tab` cycles them, `1`/`2`/`3` jump within them.

Measured after: **280 lib + 96 headless pass; the 5 remaining failures are all FVS-R-39's missing
site kit**, which was red before this work began.

---

## 1. What is there now

One binary, one door, five tabs. `tiles::Mode` is the tab (`tiles.rs:40`) with
`Mode::ALL = [Map, Meshes, Tiles, Compose, Anim]` (`tiles.rs:75`); `keys::Context` is the same five
plus `Global` and `Typing` (`keys.rs:35`); `Mode::context()` is *"the single place the two are the
same thing"* (`tiles.rs:110`). The strip is drawn from `Mode::ALL`, the number keys run in the same
order, and `the_number_keys_follow_the_strip` holds them together (`keys.rs:491`).

The chooser is already a separate process, and the reasoning is load-bearing: `Project` is inserted
before the editor's plugins, in Bevy 0.19 a missing `Res<T>` **panics its system**, and **113
parameter positions across eleven files** take `Res<Project>` or `ResMut<Project>` (comments
excluded; `chooser.rs:18` states the same fact as *"around sixty production systems across eight
files"* — a count of systems rather than of positions, and both are true). A chooser inside the
editor's `App` would mean gating all of them (`chooser.rs:14`). The same argument reaches this
design: a door that does not have a map cannot be a state inside an `App` whose systems assume one.

The menu is two coupled columns — pick a kit, then pick a map *in it*. That coupling is already
stale. Maps moved to `assets/emerge/maps/` at the project root this morning, because *"the library
that draws a map is now the merge, so filing it under one of the kits picks an arbitrary winner"*
(`project.rs:29`). Every map is in one list regardless of kit; the two columns still imply otherwise.

## 2. The model

**One tab per door, and therefore no tabs.**

| Door | The thing | What it is for | Today's tab |
|---|---|---|---|
| **Kits** | labelled meshes | bring art in, measure it, say what it is | Meshes |
| **Tiles** | one-grid-unit composures | assemble meshes into a tile a map can stamp | Tiles |
| **Compose** | larger groups | build assemblies, read their interface, see what is stale | Compose |
| **Maps** | placements + stamps | build the level | Map |
| **Rigs** | clips | preview and tune a rig | Anim |

The mapping is 1:1, which is the consequence worth naming up front: **if every door has exactly one
tab, the tab strip stops existing.** `Mode` stops meaning "which tab is showing" and starts meaning
"which door did I come through", which is a thing the author chose on a screen rather than a mode
they have to remember. That is the same move the Meshes/Tiles split already made once — *"the mode
was the giveaway: every other level already had a tab and only that one carried two. A tab strip is a
mode nobody can forget"* (`tiles.rs:71`) — carried one level up.

It also returns key budget. `Action::{NextTab, MapTab, MeshesTab, TilesTab, ComposeTab, AnimTab}`
(`keys.rs:154`) are six `Context::Global` bindings, and a Global row costs **every** context against
the twelve-row cap `no_context_carries_more_than_a_learnable_vocabulary` enforces (`keys.rs:2673`).
`rows()` collapses adjacent bindings sharing a `does`, so the five digits are one row and `Tab` is
another: the split hands **two rows back to all five contexts**, in a file where rows are the scarce
resource.

The ordering argument in `Mode::ALL` survives intact and becomes the door order. Kits → Tiles →
Compose is `docs/research/2026-08-08-kitbashing-guidance.md`'s *"parts -> sub-assemblies ->
assemblies"*; Maps is the job the other three serve; Rigs is the odd one out and goes last. The one
change is that **Maps no longer goes first**: on a menu, the hierarchy is the more useful order,
because the menu is where somebody decides what kind of work they are about to do.

## 3. What the non-Map doors actually need from a map — measured

This is the load-bearing measurement, and it came out better than expected.

`Project` is map-shaped: it carries `map`, `map_path`, `dirty` and `touched` alongside the library,
the vocabulary and the kits. Four of the five doors have no map. The naive reading of "113 positions
take `Res<Project>`" says the split is enormous.

It is not. Counting genuine field access — `.map.`, `.map,`, `.map_path`, `.dirty`, `.touched`, with
iterator `.map(` excluded:

| File | Touches | Is it the Map door? |
|---|---|---|
| `editor.rs` | 234 | **yes** |
| `chooser.rs` | 25 | no — these are `Map`/`MapEntry` values, not a `Project` |
| `project.rs` | 15 | the loader itself |
| `tiles.rs` | 9 | Kits + Tiles doors |
| `compose.rs` | 5 | Compose door |
| `build.rs` | 5 | Tiles door |
| `guided.rs` | 5 | checkpoints |

**234 of them are in the module that *is* the Map door.** And `dirty = true` is written in
**exactly one file** — `editor.rs`, 22 sites — which confirms the cut: the Meshes and Tiles doors
commit straight to disk through `tiles::commit_measured` and `Project::commit_composition`, so the
map is the only thing this editor ever holds unsaved.

So the cut is:

```
Project      root, project_dir, maps_dir, emerge_dir, namespace, library_path,
             vocab, kits, measured, library, policy, compositions, masks,
             triangles, touched, lattice          ← every door
OpenMap      map, map_path, dirty                  ← the Maps door only
```

### 3.1 And the leftovers are not map facts at all

Outside `editor.rs`, the non-Map doors read the map for exactly four things:

| Read | Sites | A fact about…? |
|---|---|---|
| `map.face_bands` | `tiles.rs:2590,6342,6356`, `compose.rs:305,1020,1879` | **the lattice** |
| `map.snap_divisor` | `compose.rs:1021,1735`, `build.rs:1472,2148` | **the lattice** |
| `map.bounds.1` | `build.rs:1135,1857,1872` — a blank tile's height | the ceiling, used as a tile default |
| `map.placements` / `map.stamps` | `tiles.rs:3473`, `guided.rs:216-241` | genuinely a map |

Three of the four are the grid, and the grid is not a property of one map.

**`face_bands` and `snap_divisor` moved onto the map this morning, and this shows the move went one
stop too far.** FVS-R-38's argument was that they describe a lattice, a map has one lattice, and two
bound kits disagreeing has no local answer — all correct, and the fix took them out of per-kit
`Policy`. But two *maps* disagreeing has no local answer either, and that is the case the door split
exposes because the Tiles door has to derive an interface with no map open at all.

Concretely: `composition::interface(comp, comps, library, per_tile)` (`composition.rs:1475`) takes
the band count as an argument, and every call site passes `project.map.face_bands`. Two maps in one
project at different band counts therefore give **the same tile two different adjacency contracts** —
a kit of tiles is only coherent at one band count. Nothing stores the wrong answer, so this is not a
corruption bug; it is that the question "what does this tile present?" currently has no answer until
you name a map, and the Tiles door is precisely the place you need one.

`snap_divisor` is the same shape: a tile whose members were seated on thirds, opened under a map at
divisor 2, has every nudge verb move it off its authored rungs.

**Proposal: `face_bands` and `snap_divisor` move once more, from `Map` to a `Lattice` on the
project.** That satisfies both arguments at once — two kits cannot disagree, and neither can two
maps — and it is the only level at which the Tiles and Compose doors can ask the question.

`map.bounds.1` is a genuine map fact being used as a tile default, which is a different problem: a
tile is a grid unit and its height should come from the kit, not from whichever map was open. It
becomes a third field on `Lattice` (`cell_height`).

`tiles.rs:3473` — folding mesh packs by whether the open map uses them — is a real cross-door
dependency and the one thing here that has to be **cut rather than moved**. On the Kits door there is
no map, so the fold has nothing to key on. See §7.

## 4. What each door loads

| Door | Needs | Does not need |
|---|---|---|
| Kits | `Project` + authoring kit | `OpenMap` |
| Tiles | `Project` + authoring kit + `Lattice` | `OpenMap` |
| Compose | `Project` + `Lattice` | `OpenMap`, an authoring kit |
| Maps | `Project` + `Lattice` + **`OpenMap`** | an authoring kit |
| Rigs | `Project` (for `rigs.ron` and the meshes) | `OpenMap`, an authoring kit |

`--kit` keeps the meaning it was given this morning — *"`--kit` chooses where new work lands, not
what the palette can show"* (`project.rs:157`) — and that meaning is now door-dependent in a way
worth stating: it is **required** for Kits and Tiles (an imported mesh and a new tile id both have to
be named in some namespace) and **meaningless** for Maps, Compose and Rigs, none of which create a
namespaced thing.

That is a refusal, not a default. A Maps door given `--kit` should say so rather than ignore it.

### 4.1 The command line

Recommended shape:

```
emerge-mapper                                  → the menu (supervisor, as today)
emerge-mapper <root> --door maps    --map <name>
emerge-mapper <root> --door kits    --kit <name>
emerge-mapper <root> --door tiles   --kit <name>
emerge-mapper <root> --door compose
emerge-mapper <root> --door rigs
```

**This retires the second positional argument.** `emerge-mapper . site_67` is documented in
`lib.rs:9` and works today; under a five-door binary a bare second positional cannot say which door
it names, and inferring one would be a second path. `--door` is required whenever the invocation is
not the menu, so there is nothing to infer.

Flagged explicitly because it is a decision that is easy to overrule: keeping `[root, map]`
positional for the Maps door alone would preserve the old invocation at the cost of one door
behaving unlike the other four.

### 4.2 The menu

Today: two coupled columns (KIT | MAP) with KIT INFO and MAP INFO panels beneath. Since maps left the
kit directories, the coupling describes nothing.

Proposed: a **door strip** across the top — the five doors, in the order above — and beneath it one
list and one info panel for whatever that door holds.

| Door | The list | The info panel |
|---|---|---|
| Kits | kits, with piece counts | KIT INFO — namespace, dir, `+ new kit`, delete |
| Tiles | compositions with a `Bounded` envelope | TILE INFO — members, interface, staleness |
| Compose | compositions with an `Anchored` envelope | GROUP INFO — same |
| Maps | maps, with placement/stamp counts | MAP INFO — name, bounds, origin, note, **kit ticks** |
| Rigs | rigs from `rigs.ron` | RIG INFO — clips, drive speed |

This is a generalisation of the screen that exists rather than a replacement: the MAP INFO panel and
its per-map kit tick-boxes — built this morning, and the reason `Field::Kit(usize)` exists
(`chooser.rs:2232`) — stay exactly where they are, under the Maps door. The piece count that the
whole chooser was written to show (`chooser.rs:11`) stays under Kits.

The **Bounded vs Anchored split between the Tiles and Compose lists is the question §9 leaves open**
in `2026-08-16-collections.md`, arriving from the other side. Making them two doors answers it by
construction, which is a reason to be confident about it and also a reason to say so out loud: the
door split is *deciding* that question, not sidestepping it.

## 5. The risk this design carries

**Menu round-trips lengthen the loop.** Labelling a mesh, building a tile out of it and placing that
tile is three doors, and under this design that is three trips through the menu — with a process
launch each way, since the doors are processes for the same `Res<Project>` reason the chooser is.

This is the design's exposure to Lai, Latham & Leymarie's second pillar, *Respect the Creative
Process* (`10.1145/3402942.3402946`): *"The creative process is a feedback loop of trying something
out, seeing the result, making changes… To stay focused on the task, it is important that this
feedback loop is as short as possible."* They take it from Compton's **grokloop** — *"the speed of
learning depends on how short the loop is"* — and the same paper is already cited at
`chooser.rs:2474` for exactly that ratio. Three relaunches to complete one thought is the tax this
design charges for the clarity it buys, and it is charged against the pillar this editor is most
often measured by.

Two mitigations, both cheap, and this doc recommends **the first only**:

- **A door key.** From inside any door, a chord that exits to the *menu with that door's row already
  under the cursor* — the supervisor's state file (`main.rs:227`) already carries a place between
  laps, so this is one more line in it, not a mechanism. Costs one `Global` row of the two the strip
  just returned.
- ~~Cross-door hop~~ — a key that jumps straight from Tiles to Kits without the menu. Rejected: it
  is the tab strip again, wearing a different hat, and it would need every door's `Project` to be
  reloadable in place, which is the teardown `chooser.rs:28` deliberately deferred.

The honest counter-argument to the whole design is that **the tab strip was not costing anything an
author complained about** — the report was that a door shows things it does not need, which is a
statement about *scope*, not about switching. A cheaper design exists: keep one window, keep the tab
strip, and have the door filter which tabs are in it. That is strictly less work and it delivers the
literal ask. It is not what is proposed here because it keeps `Mode` as a mode, keeps `Project`
map-shaped, and leaves `face_bands` where the measurement in §3.1 says it should not be — the three
things that make the current shape hard to extend. Worth knowing that the cheaper option is real.

`emerge-mapper` is a mirrored crate, so `crates/emerge-mapper/CLAUDE.md` moves with any change to the
"one plugin list, two entry points" claim — which this does touch, since `build_headless` grows a
parameter.

No golden should move: nothing here is on `FixedUpdate` and nothing reaches `snapshot_hash`. The
game's own loader reads `face_bands` off the map (`emerge-bevy/src/lib.rs:114`), so **stage 1 is the
only step a game test can see**, and it is the one to run `--workspace` after rather than
`-p emerge-mapper`. `tests/site_descriptors.rs` and `tests/importer_against_real_meshes.rs` name the
field only in doc comments recording this morning's move; they will want the same sentence rewritten
once, not new assertions.

## 7. The one thing that gets cut

`tiles.rs:3473` folds mesh packs on the Kits door by whether the open map uses them. Under the split
there is no open map, and there is no honest substitute — "used by any map in the project" would mean
parsing every map to draw a list, and "used by the last map you had open" is a fallback.

**Proposal: fold by whether the pack is in the *library*, not the map.** That is a fact the Kits door
owns, it answers the question the fold was actually for ("which of these have I already dealt with"),
and it stops changing under the author depending on which map they came from.

This is a behaviour change, not a port, and it is called out here so it is a decision rather than a
casualty.

## 8. Staging — each step a green suite

1. **`Lattice` moves off the map.** `face_bands` + `snap_divisor` + `cell_height` onto `Kits`;
   `MAP_VERSION` → 5; the 10 non-`editor.rs` sites re-point; `src/emerge_map.rs` re-points; shipped
   RON migrated one-shot. **`cargo test --workspace`**, because this is the step the game can see.
   No door work yet — this stands on its own as the FVS-R-38 correction.
2. **`OpenMap` splits off `Project`.** Mechanical, 234 sites in one module plus 5 in `guided.rs`. No
   behaviour change, no door yet — every door still loads both.
3. **`Door` replaces `Mode`.** `--door` on the command line, `Door::tabs()` is one tab, the strip
   becomes a title, the six tab actions retire. Now a door can be entered directly and shows one
   thing. **The point at which the ask is satisfied**, before the menu is touched.
4. **The menu becomes a door strip.** `Catalog` scans tiles and rigs; `launch_args` per door; the
   door key from §5. `Field::Kit` and MAP INFO stay put.
5. **Doors stop loading what they do not need.** Kits/Tiles/Compose/Rigs build without `OpenMap`;
   the pack fold changes to §7. This is the step that makes step 2 pay.

Steps 1 and 2 are worth doing whatever happens to the rest: step 1 is a correction the measurement in
§3.1 justifies on its own, and step 2 is a cut the 234-in-one-module count says is nearly free.

## 9. Open

- **Does the Rigs door belong in this binary at all?** `Mode::ALL`'s own comment already says the rig
  bench is *"a different job that happens to live in the same binary"* (`tiles.rs:58`). Under a
  five-door menu that observation gets louder — a fifth door on a menu is a stronger claim of
  belonging than a fifth tab in a strip. Not proposed either way here.
- **What does the Compose door do about `--kit`?** It authors compositions, which live in the
  project's `compositions.ron` and belong to no kit (`project.rs:552`) — so nothing. But a new
  composition still needs an id, and ids are namespaced. Either compose ids are unnamespaced (and
  `naming` has to allow it) or the door asks for a namespace at creation.
- **Bounded vs Anchored as the Tiles/Compose boundary** is decided by construction in §4.2. If that
  turns out to be the wrong line — a Bounded group larger than one cell is the obvious counterexample
  — the doors are wrong, not the panel.
- **`emerge-mapper . site_67`** stops working (§4.1). Overrulable.

## 10. What the build found: cross-door workflows — and how it was answered

**Answered by the two-door shape above; kept because it is the measurement that chose it.**

The five-door design assumed doors partition the work. Four shipped guides said otherwise — measured by counting
tab-switching steps in `guides/*.json`:

| Guide | Crossings |
|---|---|
| `room_from_nothing.json` | Meshes → Tiles → Compose → Map → Map → Compose → Map → Compose |
| `build_a_room.json` | Tiles → Compose → Map → Map → Compose → Map → Compose |
| `author_the_site_kit.json` | Tiles → Map |
| `branch_verbs.json` | Tiles → Map |

**The Compose→Map pair is the sharp one.** Compose arms a tile; the Map stamps what is armed. Those
are two halves of one act, and `ComposeState::armed` is a session resource — so a door boundary does
not merely lengthen the loop, it *loses the state the second half needs*. `build_a_room` crosses that
boundary four times.

Three things could answer it, and this document deliberately does not pick one:

1. **Compose and Map are one door.** They share a subject (what goes on the level) and the arming
   state. This contradicts the 2026-08-16 decision that Compose gets its own door — but that decision
   was taken before these numbers existed.
2. **Arming outlives the session.** Move `armed` from `ComposeState` into the project, so a door
   change keeps it. Cheap, and it makes the crossing survivable rather than free.
3. **The doors are Kit and Map, not five.** Meshes + Tiles + Compose behind one "Kit" door — which is
   close to what was actually asked for (*"if we enter a kit… we only need meshes"* plus *"tiles…
   can be used in the maps"*) — and Map separate. Two doors, no crossing inside a kit, one crossing
   between making and using.

**(3) was chosen**, and the three tests that noticed — `the_room_script_`, `the_map_script_` and
`the_repair_script_can_actually_be_followed` — pass again. (2) was not needed: with Compose inside
the Kit door, the arming state never crosses a process boundary in any shipped guide. It becomes
necessary only if a workflow later has to arm on the Kit door and stamp on the Map.
